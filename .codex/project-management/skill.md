# プロジェクト進行管理

この skill は、ProjectImacan の作業をスコープ内に収め、進捗を見える状態にし、出荷可能な単位で進めるために使用する。

## 基本姿勢

- `README.md` をプロダクト要件の基準とし、`CODEX_PROMPT.md` を実装方針の基準として扱う。
- 大きな再設計よりも MVP の完了を優先する。ユーザーが明示的に求めない限り、MVP 外の機能は入れない。
- 小さく検証可能な単位で作業する。各作業単位の完了後、リポジトリが一貫した状態になるようにする。
- 進捗を見える形にする。何を確認しているか、何が分かったか、何を変更したか、何が残っているかを要約する。
- 要件が曖昧な場合は、合理的な仮定を置いて短く明示する。誤った仮定が手戻りやリスクにつながる場合だけ質問する。

## プロジェクトスコープの基準

以下の MVP 機能を優先する。

- Discord OAuth2 ログインとバックエンドでの JWT 発行。
- JWT で保護された API アクセス。
- `CLASS`、`SELF_STUDY`、`OUT` による Presence / ステータス更新。
- Redis による Presence 保存と TTL による自動失効。
- 合計人数、授業中人数、自習中人数を返す Presence 集計 API。
- ログイン、ステータス更新、集計表示を行う React / Next.js PWA UI。

ユーザーが求めない限り、以下はスコープ外として扱う。

- リアルタイム位置追跡。
- 地図表示。
- バックグラウンドでの位置情報取得。
- 詳細なユーザープロフィール。
- 通知機能。
- 位置履歴の永続保存。

## 作業ループ

1. 現状を確認する。
   - 実装詳細を計画する前に、関連ファイルを確認する。
   - `rg` と対象を絞ったファイル読み取りを優先する。
   - 新しい実装を追加する前に、既存パターンを把握する。

2. 次に進めるべき有用な作業単位を定義する。
   - ゴールを 1 文で示す。
   - 関係しそうなファイルやモジュールを挙げる。
   - 想定する検証コマンド、または手動確認方法を示す。

3. 範囲を絞って実装する。
   - 既存構成に沿って変更する。
   - 関係のないリファクタリングは避ける。
   - ユーザーの変更や dirty worktree の状態を保持する。
   - API 変更では、リポジトリの流れに従い、まず契約の元になる定義を更新し、その後に生成コードや依存コードを更新する。

4. 検証する。
   - 最小限かつ意味のあるテストまたはビルドコマンドを実行する。
   - 検証できない場合は理由を伝え、残るリスクを明示する。
   - バックエンドとフロントエンドをまたぐ挙動では、可能な範囲で両方を確認する。

5. 明確に報告する。
   - 何が完了したかから伝える。
   - 変更ファイルと検証結果を含める。
   - ブロッカー、仮定、次に推奨する作業は、有用な場合だけ記載する。

## 計画フォーマット

簡単ではない作業では、次の簡潔な計画を使う。

```markdown
Goal: <1 文で表した達成結果>

Steps:

- [ ] <具体的な成果物がある小さな作業>
- [ ] <具体的な成果物がある小さな作業>
- [ ] <検証>

Acceptance:

- <観測できる完了条件>
- <テスト / ビルド / 確認が通ること>
```

チェックリストは最後にまとめて更新せず、作業が完了するたびに状態を更新する。

## 進捗共有

長めの作業では、短い進捗共有を行う。

- 調査中: どの文脈を集めていて、それが何を意味するかを説明する。
- 編集前: どの領域をなぜ変更するかを伝える。
- 検証中: 実行しているコマンドや確認内容を伝える。
- ブロッカー発生時: ブロッカー、試した方法、次に取るべき選択肢を説明する。

進捗共有は簡潔で、次の行動につながる形にする。

## タスク優先順位

次に取り組む作業を選ぶときは、以下を優先する。

1. MVP の次の層を解放する作業。
2. UI の磨き込みよりも、契約とデータモデルの明確化。
3. API 形状が不確かな場合は、フロントエンド統合よりもバックエンド挙動とテスト。
4. 大きな推測的アーキテクチャよりも、小さくユーザーに見える進捗。
5. 便利機能よりも、セキュリティとプライバシーの修正。

## 完了の定義

タスクは、以下を満たしたときに完了とする。

- 要求された挙動が実装されている、またはブロッカーが明確に特定されている。
- 関連するテスト、ビルド、生成コマンドが正常に実行されている。実行できない場合は理由が説明されている。
- 変更された API 契約、環境変数、起動手順がある場合、リポジトリ内の既存の記載場所に合わせて文書化されている。
- 最終報告だけで、ユーザーが diff 全体を読み直さなくても次に進める状態になっている。

## リポジトリメモ

- バックエンド: Go、TypeSpec、OpenAPI、`oapi-codegen`、Redis。
- フロントエンド: React / Next.js PWA。
- API 契約の元定義: `backend/api/typespec/`。
- 生成された OpenAPI: `backend/api/openapi/`。
- 生成された Go API コード: `backend/internal/generated/`。
- バックエンドのドメインロジック: `backend/internal/auth/`、`backend/internal/presence/`、`backend/internal/store/redis/`、`backend/internal/server/`。
