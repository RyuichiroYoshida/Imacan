# タスク管理ルール

この skill は、ProjectImacan の作業タスクをリポジトリ内で見える状態に保ち、作業の抜け漏れや重複を減らすために使用する。

## 基本方針

- リポジトリルート直下の `tasks/` をタスク管理の標準ディレクトリとする。
- `tasks/` が存在しない場合は、タスクを記録する必要が生じた時点で作成する。
- タスクは機能、領域、または目的ごとに Markdown ファイルで管理する。
- 完了したタスクは削除せず、状態を `done` に変更して履歴として残す。
- 作業開始時に既存タスクを確認し、作業完了時に進捗を更新する。
- ユーザーから明示的に不要と言われた場合を除き、現在の作業と関係するタスクだけを更新する。

## ファイル構成

タスクファイルは次の命名を基本とする。

```text
tasks/
  <area-or-feature>.md
```

例:

- `tasks/auth.md`
- `tasks/presence.md`
- `tasks/frontend-pwa.md`
- `tasks/api-contract.md`

複数領域にまたがる大きな作業は、無理に 1 ファイルへ集約せず、主な責務ごとに分ける。

## タスク形式

タスクファイルは次の形式を基本とする。

```markdown
# <機能名または領域名>

## Active

- [ ] [high] <未着手または進行中のタスク>
- [ ] [medium] <通常優先度のタスク>
- [ ] [low] <後回しでよいタスク>

## Done

- [x] [done] <完了したタスク> - YYYY-MM-DD

## Notes

- <判断理由、未確認事項、ブロッカー、関連ファイルなど>
```

## 優先度

優先度は次の 3 段階で表記する。

- `high`: 次の作業を止めているもの、MVP の成立に必要なもの、重大な不具合修正。
- `medium`: 近いうちに必要だが、他作業を直接止めていないもの。
- `low`: 改善、整理、将来対応、ユーザーが明示的に急がないとしたもの。

優先度が不明な場合は `medium` とし、`Notes` に判断理由や確認事項を残す。

## 状態管理

- 未着手または進行中のタスクは `Active` に置く。
- 完了したタスクは `Done` に移動し、日付を `YYYY-MM-DD` 形式で付ける。
- 取り下げ、重複、仕様変更で不要になったタスクは削除せず、`Done` に移して理由を短く書く。
- ブロッカーがあるタスクは `Active` に残し、行末または `Notes` に `blocked: <理由>` を書く。
- 進行中の細かいサブタスクが必要な場合は、同じファイル内でチェックリストを分けて管理する。

## 作業フロー

1. 作業開始時に `tasks/` の有無を確認する。
2. 関連しそうなタスクファイルを読み、現在の依頼と重複・矛盾がないか確認する。
3. 新しい作業が既存タスクに対応する場合は、そのタスクを更新対象にする。
4. 既存タスクがない場合は、必要に応じて適切なタスクファイルを作成または追記する。
5. 作業中に方針変更、ブロッカー、未確認事項が発生したら `Notes` に短く残す。
6. 作業完了後、完了した項目を `Done` へ移動し、残作業を `Active` に整理する。
7. 最終報告では、更新したタスクファイルと残っている重要タスクを簡潔に伝える。

## 更新基準

タスクファイルを更新するのは、次のいずれかに該当するときに限る。

- ユーザーの依頼が複数ステップに分かれる。
- 作業結果として新しい残タスク、ブロッカー、確認事項が発生した。
- 既存タスクを完了、延期、取り下げ、分割する必要がある。
- 作業の継続に必要な判断や前提を記録しておく価値がある。

短い質問への回答、単発の調査、タスク化する必要がない小さな修正では、無理に `tasks/` を更新しない。

## 完了条件

タスク管理の更新は、次を満たしたときに完了とする。

- 関連するタスクファイルに、現在の状態が反映されている。
- 完了タスクが削除されず、`Done` と日付で履歴化されている。
- 残タスクの優先度とブロッカーが読み取れる。
- ユーザーが次に何を進めればよいか判断できる。
