# ドキュメント作成ルール

この skill は、ProjectImacan のドキュメントを読みやすく、探しやすく、実装とずれにくい状態に保つために使用する。

## 基本方針

- ドキュメントの言語は原則として日本語にする。コード、コマンド、API 名、エラー名、外部仕様名は英語表記を維持する。
- 読者が次に取る行動を判断できるように書く。背景説明だけで終わらせず、必要な手順、判断基準、確認方法を含める。
- 既存ドキュメントの見出し階層、表記、粒度に合わせる。新しい構成を作る前に、同じ種類のドキュメントがないか確認する。
- README はプロダクト要件と全体像、`docs/` は補足設計や運用メモ、各サブディレクトリの README はその領域の使い方に絞る。
- 実装と矛盾する推測を書かない。未確定事項は「未決」「仮定」「今後確認」と明示する。
- MVP 外の内容は、ユーザーが求めた場合だけ追加する。追加する場合も、MVP との関係が分かるように分離する。

## 配置基準

- `README.md`: ProjectImacan の目的、MVP スコープ、主要要件、利用者に見える仕様。
- `docs/`: ディレクトリ構成、設計判断、運用手順、開発者向け補足、長くなる説明。
- `backend/api/typespec/README.md`: TypeSpec、OpenAPI 生成、API 契約の扱い。
- 実装ディレクトリ直下の README: そのディレクトリで作業するために必要な最小限の前提、コマンド、注意点。

迷った場合は、最も長く保守される情報を `docs/` に置き、入口になる短い案内だけ README からリンクする。

## 構成テンプレート

新しいドキュメントは、目的に応じて以下の順で構成する。不要な章は省略してよい。

````markdown
# <ドキュメント名>

## 目的

<この文書で判断できること、または実行できること>

## 背景

<必要な前提。長くしすぎない>

## 方針

<採用するルール、設計、運用方針>

## 手順

1. <具体的な操作>
2. <具体的な操作>
3. <確認>

## 確認方法

```bash
<検証コマンド>
```

## 注意点

- <既知の制約、未決事項、リスク>
````

仕様や設計メモでは、必要に応じて「対象」「非対象」「データ構造」「API」「失敗時の挙動」「セキュリティ / プライバシー」を追加する。

## 表記ルール

- 見出しは短く具体的にする。曖昧な「概要」「詳細」だけで階層を増やさない。
- 箇条書きは同じ文型でそろえる。手順は番号付きリスト、並列の要件や注意点は箇条書きを使う。
- コマンド、パス、環境変数、ステータス値、API パスはバッククォートで囲む。
- サンプルコードには言語名を付ける。JSON、YAML、Go、bash などを明示する。
- 日付や時刻、TTL、ポート番号、ステータス名などの値は、実装または要件と一致していることを確認してから書く。
- 「すること」「できること」「してはいけないこと」を混ぜず、読み手が判断しやすい単位に分ける。

## 更新ワークフロー

1. 既存文書と実装を確認する。
   - `rg` で同じ用語、API パス、コマンド、設定名を検索する。
   - 実装、TypeSpec、OpenAPI、Taskfile、README のどれが情報源かを確認する。

2. 変更範囲を決める。
   - 既存文書への追記で済む場合は、新規ファイルを増やさない。
   - 長くなる場合は `docs/` に分離し、入口になる文書からリンクする。

3. 文書を更新する。
   - 実装済みの内容と、未実装または未決の内容を区別する。
   - 生成物や外部ツールの出力をそのまま長く貼らず、必要な読み方と再生成手順を優先する。
   - 関連するコマンドがある場合は、作業ディレクトリが分かる形で記載する。

4. 整合性を確認する。
   - リンク先、ファイルパス、コマンド、API パスが存在するか確認する。
   - 実装変更に伴う文書更新では、変更した仕様が README や `docs/` と矛盾していないか確認する。

5. 報告する。
   - どの文書を何の目的で更新したかを短く伝える。
   - 未確認事項や、実装側に残る差分がある場合は明示する。

## 完了条件

ドキュメント作業は、以下を満たしたときに完了とする。

- 読者、目的、配置場所が明確である。
- 日本語を基本とし、コードや固有名詞の表記が一貫している。
- 関連する実装、コマンド、API 契約、既存ドキュメントと矛盾していない。
- 手順がある場合、実行順と確認方法が分かる。
- 未決事項や仮定が、確定事項のように書かれていない。
